# Programmatic SEO (pSEO): templated pages at scale, safely

Programmatic SEO means generating many pages from **one template + a dataset**
(e.g. "<tool> integrations with <app>", "<cost> in <city>", "<currency A> to
<currency B>"). Done well it serves thousands of real long-tail queries. Done
badly it is exactly what Google's spam policies call **scaled content abuse** or
**doorway abuse** — and the penalty usually hits the whole site, not only the
generated pages.

Rule of thumb: **each page must answer a real query with information the user
cannot get from the sibling page by swapping one word.**

## 1. Is pSEO appropriate? (go / no-go)

Answer all five before building. Any "no" → don't scale; build a few hand-made
pages instead.

| # | Question | Go if… |
|---|----------|--------|
| 1 | Is there a repeatable query pattern with real demand? | Keyword research (`keyword-research.md`) shows many variants with impressions/volume, and the SERP for them shows **specific** pages, not generic guides |
| 2 | Does each variant need a different answer? | The correct answer changes materially per variant (price, specs, availability, rules, data) |
| 3 | Do you own or can you legitimately use the data? | Licensed, first-party, public-domain, or properly attributed — not scraped from a competitor |
| 4 | Can the data be kept fresh? | There's a refresh pipeline and an owner |
| 5 | Would the page be useful with no search engine at all? | A visitor arriving from a link would still find it worth reading |

## 2. Data-source quality

The dataset *is* the content. Audit it before the template:

- **Coverage:** % of rows with every field the template needs. Rows below the
  minimum field set get no page (see empty states, §6).
- **Accuracy:** spot-check 20 random rows against a primary source; record the
  error rate. > 5% errors → fix the pipeline before publishing.
- **Freshness:** last-updated per row; display it on the page.
- **Uniqueness:** how many fields actually differ between neighbouring rows? If
  only the name/city differs, the pages will be near-duplicates.
- **Provenance & rights:** document where each field comes from and that you may
  use it. Cite the source on-page where it builds trust.

> If the user can't supply the dataset or a sample of it, mark the pSEO
> assessment **INSUFFICIENT DATA** — the template can't be judged without it.

## 3. URL patterns

- One stable, readable pattern per page type: `/integrations/<app>/`,
  `/<service>/<city>/`, `/convert/<from>-to-<to>/`.
- Lowercase, hyphenated slugs; no IDs or query parameters in indexable URLs.
- **One canonical order** for combinations (`usd-to-eur` exists; `eur-to-usd` is a
  separate page only if the answer differs — otherwise canonicalise or don't
  generate it).
- Avoid deep combinatorial paths (`/<a>/<b>/<c>/<d>/`) — they explode the URL
  count without matching real queries.
- URLs must never change when the dataset is re-generated (stable slugs,
  stored, not recomputed from mutable fields).

## 4. Per-page uniqueness requirements

Each generated page needs, at minimum:

1. **Unique primary data** — the row's own values, presented prominently (a
   table, specs, numbers, map, prices).
2. **Derived insight** — something computed from the data that isn't on sibling
   pages: rankings, comparisons to the average, trends, "cheapest/fastest",
   warnings.
3. **Variant-specific copy** — intro and summary that change in substance, not
   just in the swapped noun. Text generated by an LLM per row counts only if it
   adds facts from the data, and it must be sampled and reviewed (§5).
4. **Useful extras where the data supports it:** FAQs answered from row data,
   user reviews/UGC, images of the actual item/place, local details.
5. **Unique title, meta description and H1** built from row fields.

**Uniqueness check:** take two random sibling pages, strip the shared template
chrome, and compare the remaining main content. If more than about half is
identical sentences, the template is too thin. (A rough heuristic, not a Google
threshold — Google judges usefulness, not a percentage.)

## 5. Spam-policy risk and quality gates

Google's spam policies name the patterns pSEO is most likely to trip:

- **Scaled content abuse** — generating many pages mainly to manipulate rankings
  rather than help users, whether by automation, humans, or both.
- **Doorway abuse** — many pages targeting similar queries (e.g. one per city)
  that funnel users to the same place or offer little unique value.
- **Thin affiliate pages** — product data copied from a merchant with no added
  value.
- **Scraping** — republishing others' content without adding value.

🔴 **Warn loudly** when you see: large location-page sets where only the city name
changes; "best <X> in <every town>" pages with no local data; one page per
keyword synonym; AI-written pages published unreviewed at scale; pages generated
for combinations nobody searches.

**Quality gates (in order — do not skip):**

1. **Template review** — build the template with 3 real rows (best, average,
   worst data). Review against §4 and `content-strategy.md` quality rubric.
2. **Sample batch** — publish 20–50 pages (indexable) and leave the rest
   unpublished. Wait 4–8 weeks.
3. **Measure** — in GSC: what share got indexed? impressions? any "Crawled –
   currently not indexed"? If under ~half are indexed, Google is telling you the
   pages aren't worth it — improve the template, don't scale.
4. **Scale in steps** — expand by roughly an order of magnitude at a time,
   re-checking indexation each step.
5. **Ongoing sampling** — each month, read 10 random pages for errors, empty
   blocks and stale data.

## 6. Indexation control

| Situation | Control |
|-----------|---------|
| Row lacks the minimum data (empty state: "no results in <city>") | Don't generate, **or** serve with `noindex` and exclude from sitemaps. Return 404/410 if the item doesn't exist |
| Two variants have the same answer | `rel="canonical"` to the main one; don't list the duplicate in sitemaps |
| Filter/sort/pagination parameters | Canonical to the clean URL; keep parameter URLs out of sitemaps and internal links |
| Retired items | 301 to the closest equivalent, or 410 if none (`redirects.md`) |
| Pages still being tested | `noindex` until they pass the gates |

**Sitemap segmentation:** one sitemap per template/type (`sitemap-integrations.xml`,
`sitemap-cities.xml`), each ≤ 50,000 URLs / 50 MB uncompressed, tied together by a
sitemap index. Segmentation makes GSC show indexation **per template**, which is
how you catch a failing template. Only list canonical, indexable, 200-status URLs,
with real `lastmod` dates.

## 7. Internal linking for large page sets

- **Hub pages** per dimension (`/integrations/`, `/locations/<state>/`) that link to
  every child — paginated or grouped, real `<a href>` links, not JS-only.
- **Breadcrumbs** (with `BreadcrumbList` schema) from each child up the hierarchy.
- **Sibling links** chosen by relevance (nearby cities, similar products, related
  integrations) — 5–15 per page, not hundreds.
- **Editorial links** into the best-performing generated pages from pillar
  content (`internal-linking.md`).
- Check click depth: every indexable page reachable in ≤ 4 clicks from the home
  page; no orphans (a page in the sitemap but not linked anywhere).

## 8. Monitoring index bloat in GSC

Run monthly; record in the baseline (`diagnostics.md` Part C).

1. **Page indexing report**, filtered by each segmented sitemap: indexed vs
   submitted ratio per template.
2. Watch the "**Crawled – currently not indexed**" and "**Discovered – currently
   not indexed**" counts. A rising trend on one template = Google is devaluing it.
3. **Duplicate, Google chose different canonical than user** → near-duplicate
   variants; merge or differentiate.
4. **Performance** by URL pattern (filter page contains `/integrations/`): share of
   pages with ≥ 1 click in 90 days. Pages with zero impressions after 6 months are
   candidates for noindex/removal (`content-strategy.md` page verdicts).
5. **Crawl stats**: is Googlebot spending its crawls on low-value variants instead
   of important pages?

**Decision rule:** if a template's indexed share is low *and* falling, or
sitewide quality metrics dropped after a launch, pause generation, prune the
weakest rows (noindex or 410), and improve the template before resuming.

## Output

Report as an audit section with: go/no-go table (§1), data-quality findings,
template uniqueness verdict, spam-risk flags with severity, gate status, and a
fix list (feed into `templates/fix-report-template.md`).
