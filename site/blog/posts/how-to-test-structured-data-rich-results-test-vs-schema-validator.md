Use the Rich Results Test to check whether a page is eligible for a Google rich result, and the Schema Markup Validator to check whether your schema.org markup is valid in general. They answer different questions. The Rich Results Test only knows the types Google supports. The validator knows every schema.org type but nothing about Google's required properties. A solid workflow uses both, then confirms with URL Inspection and the Search Console enhancement reports.

**Key takeaways**

- Rich Results Test: Google eligibility, rendered page, about 40 supported features. Retired types like FAQ no longer appear.
- Schema Markup Validator: syntax and vocabulary for any type, with no Google eligibility rules.
- URL Inspection: proves Google's own crawl of the live page contains your markup.
- Search Console enhancement reports: catch errors across thousands of URLs after a release.
- None of them checks that the markup matches the visible page. You have to do that yourself.

## The four tools at a glance

| Tool | Answers | Input | Renders JavaScript | Covers |
|---|---|---|---|---|
| [Rich Results Test](https://search.google.com/test/rich-results) | "Can this page get a Google rich result?" | Public URL or pasted code | Yes, as Google-InspectionTool | Google-supported rich result types only |
| [Schema Markup Validator](https://validator.schema.org/) | "Is this valid schema.org?" | URL or pasted code | Yes, for URLs | Every schema.org type |
| URL Inspection (Search Console) | "What did Google actually see on my live page?" | A URL on a verified property | Yes, the live or indexed render | Detected rich result types for that URL |
| Enhancement reports (Search Console) | "Which pages across my site have errors?" | Automatic, from Google's crawl | n/a | Each supported feature with a report |

The validator is the successor to Google's old Structured Data Testing Tool, now hosted by schema.org. It's the tool to use when you're checking types Google doesn't turn into rich results, such as `Person`, `Service` or `WebPage`, or legacy markup like `FAQPage`.

## What the Rich Results Test tells you

Google's [Rich Results Test help page](https://support.google.com/webmasters/answer/7445569) describes its behavior:

- It fetches the URL with a smartphone user agent by default. You can switch to desktop.
- It renders the page, so markup injected by JavaScript is tested.
- It reports each detected item as valid, valid with warnings, or invalid.
- It shows the rendered HTML, so you can see what the crawler actually got.

**Errors** mean an item is invalid and can't produce that rich result: a missing required property, bad syntax, or a URL Google couldn't crawl. **Warnings** mean the item is valid but missing recommended properties, or some resources didn't load. Fix errors first. Warnings are worth fixing when the property is true and easy to add, not by inventing values.

### Its blind spots

- It can't test pages blocked by robots.txt, behind a firewall or behind a login. For staging, paste the code or use a public tunnel.
- It doesn't support every structured data use. Site names, for example, aren't tested there, as Google's site names doc notes.
- Retired features disappear from it. After the 2026 FAQ deprecation, a page with valid `FAQPage` markup shows no FAQ item at all. That isn't an error.
- The preview isn't a promise. Google says results may differ from what the tool shows.
- It ignores JSON-LD comments, but real parsers may not. Remove comments before publishing.

## What the Schema Markup Validator tells you

The validator parses JSON-LD, Microdata and RDFa, then shows each entity it found with its properties. It flags:

- JSON syntax errors that stop parsing.
- Properties that don't exist in schema.org, such as a typo like `datePublised`.
- Values of the wrong type, where schema.org expects something else.

What it won't flag is a `Product` with no `offers`, or an `Event` with no address. Those are valid schema.org and invalid for Google. A green result in the validator doesn't mean a page is eligible for anything.

## URL Inspection: the ground truth

The Rich Results Test does a fresh fetch. URL Inspection in Search Console shows what Google stored for that URL in its index, and "Test live URL" shows a fresh render through Google's indexing pipeline. Use it when:

- The Rich Results Test passes, but Search Console reports nothing for that page.
- Your markup is generated by JavaScript and you want to confirm it survives rendering. [JavaScript SEO](/blog/javascript-seo-making-react-vue-and-next-js-sites-crawlable/) covers why client-rendered content sometimes doesn't.
- You suspect a CDN, bot protection or a consent wall serves Googlebot a different page.

Check the "View crawled page" HTML for your `application/ld+json` block. If it's missing there, no amount of markup tuning will help.

## Search Console enhancement reports

Once pages are indexed, Search Console groups structured data issues by feature: Product snippets, Merchant listings, Breadcrumbs, Videos, Events, Review snippets, Profile page, Discussion forum and others. These reports are where template bugs show up, because one broken template produces the same error on hundreds of URLs.

After fixing an issue, use "Validate fix" in the report. Google recrawls a sample of affected pages and updates the status over the following days.

## A testing workflow that catches most problems

1. **While building:** paste the JSON-LD into the Schema Markup Validator to catch syntax and vocabulary errors.
2. **On staging:** paste the rendered HTML or code into the Rich Results Test to check Google's required properties for the target type.
3. **After deploy:** test two or three live URLs per template in the Rich Results Test.
4. **For JavaScript-rendered markup:** run URL Inspection's live test on one URL per template and confirm the JSON-LD appears in the rendered HTML.
5. **Within a week:** check the enhancement reports for new errors and validate fixes.
6. **Every time:** compare marked-up values (price, rating count, dates, author) with what the page displays.

Step 6 is the one tools skip. Google's [general guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) say markup must represent the visible content, and a page can fail that rule while passing every validator.

## Automating the basics

You can catch the most common failure, a JSON-LD block that doesn't parse, in CI before anything reaches production. Here's a minimal Python check that fetches a page and parses every JSON-LD block:

```python
import json
import re
import sys
import urllib.request

url = sys.argv[1]
html = urllib.request.urlopen(url, timeout=20).read().decode("utf-8", "replace")
blocks = re.findall(
    r'<script[^>]+type=["\']application/ld\+json["\'][^>]*>(.*?)</script>',
    html, re.S | re.I)
if not blocks:
    sys.exit("No JSON-LD found in raw HTML: " + url)
for i, block in enumerate(blocks, 1):
    try:
        data = json.loads(block)
    except json.JSONDecodeError as e:
        sys.exit("Block %d is invalid JSON: %s" % (i, e))
    items = data if isinstance(data, list) else data.get("@graph", [data])
    print(i, [item.get("@type") for item in items])
```

This checks the raw HTML only, so it won't see markup added by JavaScript. Run the Rich Results Test or URL Inspection for those pages. It also doesn't check Google's required properties. Treat it as a smoke test, not a replacement for the tools above.

## Matching symptoms to tools

| Symptom | Start with |
|---|---|
| "Unparsable structured data" in Search Console | Schema Markup Validator on the exact URL |
| Rich result never appears though markup looks right | Rich Results Test, then URL Inspection |
| Errors on hundreds of pages after a release | Enhancement report, then one URL in the Rich Results Test |
| Markup present in source but not detected | URL Inspection rendered HTML |
| Custom or non-Google types | Schema Markup Validator |
